=========== BAGIAN C - METHOD OVERLOADING ===========

Alasan penggunaan : satu nama method melayani kebutuhan berbeda, sehingga
                   pemanggil tidak perlu menghafal banyak nama method.

[P6.6] BankSampah.cariSampah() di-overload 3 kali:
  cariSampah("SP-002")        -> Koran Bekas
  cariSampah("Logam", 10000.0) -> 1 data: SP-003 Kaleng Bekas
  cariSampah(5000.0)           -> 2 data: SP-001 Botol Plastik PET, SP-002 Koran Bekas
  Alasan: kode sampah unik, sedangkan jenis dan batas harga dapat cocok
          dengan banyak data sekaligus.

[P6.7] Rekening.tambahSaldo() di-overload 2 kali:
  tambahSaldo(2500.0) tanpa keterangan:
  tambahSaldo(7500.0, "Setoran Sampah Logam") dengan keterangan:
Setoran Rp7.500 (Setoran Sampah Logam) masuk ke rekening R-NS-001
  Alasan: variant berketerangan dipakai saat setoran perlu dicatat
          sumbernya pada laporan.

[P6.8] Koperasi.tambahAnggota() di-overload 2 kali:
  jumlah anggota sebelum : 45
  tambahAnggota()       -> 46 anggota
  tambahAnggota(3)      -> 49 anggota
  Alasan: pendaftaran perorangan memakai tanpa parameter, sedangkan
          pendaftaran massal memakai jumlah sekaligus.

[P6.9] KatalogEntitas.cari() di-overload 3 kali pada collection polimorfik:
  cari("Budi")            -> Budi (Nasabah)
  cari(10000.0)          -> 3 entitas: Budi, Bank Sampah PENS, Koperasi Sampah Sumenep
  cari("Nasabah", 1000.0)   -> 1 entitas: Budi
  Alasan: kunci pencarian dapat berupa nama, ambang nilai kontribusi,
          atau kombinasi keduanya.

=========== BAGIAN D - UPCASTING & POLYMORPHIC REFERENCE ===========

[P6.10] Upcasting eksplisit dari reference subclass ke superclass:
  tipe reference awal    : Nasabah
  tipe reference akhir   : Entitas
  tipe object sebenarnya: Nasabah
  nama tetap terbaca    : Budi
  peran yang berjalan   : Nasabah

[P6.11] Upcasting langsung pada deklarasi (bentuk ringkas):
  tipe reference : Entitas, Entitas, Entitas
  tipe object    : Nasabah, BankSampah, Koperasi
  nama            : Dewi, BS Mitra, Koperasi Bakti
  peran           : Nasabah, Bank Sampah, Koperasi

[P6.12] Polymorphic reference: reference superclass, object subclass:
  bank.getClass() = BankSampah -> peran Bank Sampah
  kop.getClass()  = Koperasi -> peran Koperasi
  Superclass Entitas hanya membutuhkan method getPeran() yang di-override,
  sehingga reference superclass tetap memancing behavior spesifik subclass.

=========== BAGIAN F - PENGUJIAN DYNAMIC BINDING ===========

Setiap reference bertipe Entitas, tetapi method yang dieksekusi berbeda.

No | Tipe Reference | Tipe Object   | Method          | getPeran()  | hitungKontribusi()
---+----------------+---------------+-----------------+-------------+------------------
1  | Entitas        | Nasabah       | tampilkanPeran() | Nasabah     | Rp20.000
2  | Entitas        | BankSampah    | tampilkanPeran() | Bank Sampah | Rp19.500
3  | Entitas        | Koperasi      | tampilkanPeran() | Koperasi    | Rp75.000.000

Pembuktian:
  nas.getClass()   = Nasabah
  bank.getClass()  = BankSampah
  kop.getClass()   = Koperasi
  Ketiganya dipanggil melalui method yang sama pada reference bertipe
  Entitas, tetapi tiga implementasi berbeda yang dieksekusi.

Mengapa method yang dijalankan berbeda walaupun reference bertipe sama?
  1. Reference hanya menyimpan tipe statis (Entitas) dan alamat object di memory.
  2. Saat runtime, JVM membaca tipe aktual object pada object header, yaitu
     Nasabah, BankSampah, atau Koperasi.
  3. JVM mencari method dengan nama, parameter, dan return type yang cocok pada
     tipe aktual tersebut, bukan pada tipe reference.
  4. Karena setiap subclass meng-override method, implementasi yang dipanggil
     adalah milik subclass. Proses ini disebut Dynamic Binding atau
     Dynamic Method Dispatch, dan terjadi saat runtime.

Konsekuensi : menambah subclass baru di P7 tidak mengubah loop pada
collection, cukup menambah satu class baru.
